# Hammerspoon 配置

Lin 的 macOS Hammerspoon 配置。围绕「蓝牙键盘 / 鼠标 / 触控板」的输入体验定制，附带窗口、截屏等常用工具。

## 模块一览

### init.lua — 加载入口

按依赖顺序 require 各模块（`osk` 必须在 `kbswap` 之前，因为 kbswap 的图标点击回调要调 osk 暴露的开关）。

当前停用（文件保留、取消注释即可启用）：

| 模块 | 停用原因 |
| --- | --- |
| `scroll` | Lin 于 2026-10-01 手动注释停用（与反转滚动的使用习惯冲突） |
| `clipboard` | 2026-10-01 已整理掉全局变量污染，待重新启用 |
| `weather` | 2026-10-01 已改为读环境变量，**需先配置 `TIANQI_APPID` / `TIANQI_APPSECRET`** |
| `axkeyboard` | 备用方案，功能正常但每次要经过系统设置 |

### kbswap.lua — 蓝牙键盘 ⌘/⌥ 对调 + 菜单栏键盘图标

- **为什么不用系统「键盘 → 修饰键」**：macOS 那个设置按键盘记录，但被识别成 BLE 的键盘（MX Keys、Lofree 等）根本不在下拉列表里。
- 引擎一 `hidutil`（默认）：向蓝牙键盘自己的 HID 服务下发映射表，只对调这一把键盘的 ⌘ 与 ⌥，内置键盘不受影响。
- 引擎二 `eventtap`（兜底）：事件流层面全局交换，蓝牙键盘连着时内置键盘也会一起换；仅在 hidutil 不灵时用。
- 热键 `⌃⌥⌘K` 切换模式；菜单栏显示键盘图标（实心 = 蓝牙键盘在线，斜杠 = 离线），**点击图标 = 开关屏幕键盘**（osk.lua），键盘上下线时弹提示。
- ⚠️ **前提是 Hammerspoon 自己在跑**：映射挂在 HID 层，键盘一重连 / 机器一唤醒就丢，全靠这个进程每 5 秒重挂一次。**进程不在 = 功能不在**（2026-10-06 实锤：进程中午 12:21 退出后一整天没起来，交换就"坏了"）。所以 `init.lua` 里加了 `hs.autoLaunch(true)` 让它登录后自启；不想要就删那一行。
- 排查第一步永远是**看菜单栏图标在不在**。图标在却不交换，看 tooltip：有设备却挂不上会写「下发失败：…」，不会再用「待机（无蓝牙键盘）」糊弄（旧版会谎报，2026-10-06 修）。
- **响应速度**：轮询 2 秒一轮（`M.pollInterval`），每轮对已挂载的键盘做一次 `--get` 读回（`hidutil property --get` 实测 <10ms，开销可忽略）。
  判定「已经挂好」的依据**只有一个：把设备上的映射读回来核对**。
  它取代了原来的时间判据（`sig 没变 + 距上次不到 reassert`）——映射会随键盘服务被移除而丢失，而同一把键盘重连后的 RegistryID 常常一模一样（Flow84 一直是 `0x1000256da`），那个判据会错满 60 秒，表现就是「键盘连上了，好一会儿才交换」。
  它也取代了 `reassert` 的兜底重挂：每 2 秒就核对一次，休眠唤醒两秒内就能发现，不必每分钟无谓地重写一遍 HID 属性（`M.reassert` 字段保留但不再参与判定）。
  读回必须**按设备自己的 RegistryID 逐台查**：匹配退到 Transport 兜底时会同时命中蓝牙鼠标，读回输出里混着别人的映射，只看「值在不在」会把鼠标的映射当成键盘的。
  **实测延迟**（2026-10-17 真机日志）：拔掉 → 插上 → 交换生效约 **8~10 秒**，其中 6~8 秒是 macOS 蓝牙栈自己建 HID 服务的时间（那段时间设备还不在 `hidutil list` 里，我们看不见也做不了），发现之后只花 **2 秒**（一个轮询周期）挂上。修复前最长要等 60 秒。
- **状态日志** `~/.hammerspoon/.workbuddy/kbswap.log`：只记变化（设备出现/消失、下发成败、读回发现映射被收走），带**完整年份**的时间戳（`2026-10-17 22:15:24`），超过 512 KB 自动截断。排查"键盘连上后多久才交换"直接看它。

### osk.lua — 屏幕键盘（现行方案）

蓝牙键盘不在手边时，用鼠标 / 触控板 / 触摸屏给前台 App 打字的全功能键盘：

- **洛菲小顺 75% 布局**，6 行 85 键，每行恒宽 **16 单位**（2026-10-05 从 86 键布局改过来，
  按 Lin 提供的洛菲小顺实机照片 1:1 排布）：
  - 顶排：esc + F1~F12 + **⌘C / ⌘V / ⌦**（对应实机的 PrtSc / Ins / Del 位，见下条）；
  - 主键区右侧是**导航列**：home / end / pgup / pgdn 从上到下一列（实测像素级对齐）；
  - 方向键按实机排布：**↑ 在右 ⇧ 右侧、←↓→ 在底排最右**，↑ 与 ↓ 左缘像素级对齐；
  - 底排：⌃⌥⌘ · 空格 · ⌘ · **fn** · ⌥⌃（洛菲顺序，fn 在空格右侧）+ ←↓→；
  - 数字行右端标 **Backspace**（不是 Delete：`hs.keycodes` 的 `delete` 就是退格），
    顶排右端那个才是 **Del**（向前删除）；两者都用**字母**标注
    （2026-10-05 Lin 要求：图标不够明显）；
  - ⌫ / ⌦ / 方向键按住连发；修饰键 sticky（点一下上膛、作用于下一键）；caps 为纯内部状态。
  - ⚠️ **对齐的判据是「累计单位位置」，不是「每行键宽合计」**：build() 里
    `x_i = pad + P_i*(unit+gap)`、右缘 `= pad + (P_i+w_i)*(unit+gap) - gap`，
    只跟该键之前所有键的宽度之和有关，**跟这一行有几个键无关**。
    「每行键宽合计相等」在各行键数不同时**并不等于**对齐——别拿单位数当判据，
    直接测像素右缘（测试 13.1）。现在六行最右缘实测全部 877.80，完全齐平。
  - 右 ⇧ 是 **1.75**（不是常见的 2.75）：原先是「1.5 + 留白 0.25」，那条留白在
    面板上就是 ⇧ 与 ↑ 之间一条 17.85px 的空缝（标准 gap 才 4.20px）。把 0.25
    并进键宽、撤掉留白后，↑ 的累计位置**不变**（仍 14.0，与 ↓ 对齐），
    缝隙缩到标准的 4.20px。
- **没有 PrtSc / ScrollLock / Pause / Insert**：**Mac 键盘物理上没有**，且
  `hs.keycodes.map` 里确实没有 `print` / `scrolllock` / `pause` / `insert` 这几个名字
  （不是文档漏写——在 `libkeycodes.dylib` 的键名表里同样搜不到）。写进布局不会报错，
  `keyStroke` 只会**静默打空**。Lin 拍板：实机的 PrtSc / Ins 两个键位改成
  **⌘C（拷贝）/ ⌘V（粘贴）组合键**（`def.combo`，整组直发、不掺 sticky 状态）。
  测试里有一道守门员断言钉死这件事，别再加回 `print` / `insert`。
- **组合键（`def.combo = {mods={...}, k="..."}`）**：整组直发，**不掺 sticky 修饰键**
  （上着 ⇧ 点 ⌘C 出来的仍是纯 ⌘C），发完照例清空 armed。combo 键的 `def.k` 故意是
  nil（防止被误当普通键发出垃圾），所以 `labelFor` / 键名守门员里都必须先挡 `def.combo`。
- **FN 是 sticky 修饰键**：点一下上膛（键帽变高亮），作用于下一个键后自动松开。
- **FN 还要「真发一次 fn 键」（2026-10-05 修）——这是 Lin「FN 按了没用」的根因**：
  光上膛只是改了我们自己的 `M.armed`，**一个键都没发出去**。那些「连按两次 Fn」类
  的系统快捷键（macOS 听写默认就有：系统设置 → 键盘 → 听写 → 快捷键 →
  「按 Fn 键两次」）因此永远收不到事件。现在 `tapFnKey()` 每点一次 FN 就真的发一次
  **fn 按下 + 抬起**：点一下 = 真按一次，连点两下 = 真按两次 = 双击 Fn。
  - ⚠️ **不能用 `hs.eventtap.keyStroke({"fn"}, "fn")`**：keyStroke 把同一份 mods
    同时用在按下和抬起两个事件上（见 `eventtap.lua` 源码），抬起事件里 fn 标志位
    仍然是 1 ⇒ **系统会认为 fn 一直按着没松**。必须手工发
    `newKeyEvent({"fn"}, "fn", true)` + `newKeyEvent({}, "fn", false)`。
  - **有实体存档时改成「原样录 + 原样回放」**（`fn-event.dat`，2026-10-05）：
    探针实测实体 FN 走 `systemDefined`（`keyCode=0`，flags 含 `0x800000`），
    而合成的 `newKeyEvent({"fn"},"fn")` 是 `keyDown/keyUp` —— **形态完全对不上**。
    于是用 `ev:asData()` 把实体事件序列化存档，回放时 `newEventFromData()` 原样
    重建，不必搞懂 subtype/data1 是什么。
    - ⚠️ **一次实体敲击 = 4 条事件，不是「一个 down + 一个 up」**：
      ① `systemDefined` kc=0 flags=`0x20800000`（按下）
      ② `flagsChanged` kc=63 flags=`0x20800000`（按下伴随，+0.5ms）
      ③ `systemDefined` kc=0 flags=`0x20000100`（**抬起**，约 +70ms）
      ④ `flagsChanged` kc=63 flags=`0x20000100`（抬起伴随）
      头两版按「交替落位」存，把 ② 当成抬起 ⇒ 档是 down+down，回放等于按住不松。
      **破绽在间隔里：存下来的 down→up 只有 0.2ms，人手做不到。**
      判据因此改成按 **fn 标志位分组**（为 1 全归按下组、为 0 且已处于敲击中全归
      抬起组），整串按实测间隔回放。
    - 存档只有一半（缺按下或缺抬起）**一律不采纳**，退回手工合成 —— 半个档用起来
      等于把 FN 按死，比没档更糟。控制台 `hs.osk.fnDataStatus()` 看当前档，
      换键盘后重录：`M.fnCaptureOn = true` → Reload → **慢慢按实体 FN 一下** →
      日志出现「一次敲击采集完成」即可。`M.fnReload()` 可不重启重读。
      探针日志在 `M.probeLog`（默认 `~/.hammerspoon/.workbuddy/hs-fn-probe.log`，
      **不放 /tmp** —— 藏在 /tmp 里等于没写）。
- **听写键（顶排最右，2026-10-05）**：发 `M.dictationCombo`（默认 **⌃⌥Space**）。
  ⚠️ **屏幕键盘唤不出 macOS 的「按 Fn 键两次」听写**——四轮真机实测：实体 FN 的
  事件录得到、原样回放也发得出去，但系统的听写检测在 **HID 层认事件来源**，
  合成事件不认。**这条路已经堵死，别再钻了。**
  ⇒ 改发普通组合键：把「系统设置 → 键盘 → 听写 → 快捷键」设成 ⌃⌥Space（或你
  顺手的组合，改 `M.dictationCombo` 一行即可），屏幕键盘点「听写」、实体键盘按
  同一组合都能唤出。顶排右端四键（⌘C/⌘V/⌦/听写）各 0.75 单位给它腾位。
- **FN 换键层（2026-10-05）——为什么不能直接发 fn+键**：实体键盘的 FN 是**固件层**
  的东西：按 FN+F1 时键盘自己换了一个 HID usage 码发给电脑（F1 → 亮度减），
  **macOS 从头到尾没收到过「fn 修饰键」**，`fn` 只是事后补出的标志。软件键盘只能
  发 CGEvent，给事件挂 `fn` 标志位**绝大多数 App 直接忽略**（它们本来就没打算处理
  fn），于是不管怎么点都没反应 —— 这就是它跟实体 FN 不一样的根本原因。
  所以 `FN_MAP` 在**发送端就把键换掉**，模拟固件干的那件事：
  - F1/F2 → 亮度减/加；F7~F9 → 上一首/播放/下一首；F10~F12 → 静音/音量减/加
    （这几个只能走 `hs.eventtap.event.newSystemKeyEvent`，`keyStroke` 打不出来）；
  - fn+←/→/↑/↓ → home/end/pageup/pagedown；fn+Delete → 向前删除（Mac 惯例）；
  - 换键**保留**其它 sticky 修饰键：fn+⇧+← = ⇧+home（选到行首），跟真机一致；
  - F3~F6（调度中心/启动台/听写）没有对应的系统键，原样挂 fn 标志位透传。
  ⚠️ 新增修饰键时 `M.armed` 的**初始化**与 `sendKey()` 里的**清空表**必须两处一起改。
- **点击不抢焦点**（v3 根治版）：键盘显示期间挂 session 级 eventtap，凡落在面板内的鼠标事件一律在上游截获丢弃——AppKit 看不见点击，焦点始终留在目标 App，合成按键直达输入框。
- 面板可拖动（按住顶部把手条 / 键位缝隙拖），`M.scale`（默认 1.4）统一缩放整体尺寸，触摸屏使用友好。拖动越界会被钳制在主屏内，避免面板被拖丢找不回来。
- **显示时避开输入区**（`M.avoidInput = true`）：打开前用 AX 定位当前输入区，然后把面板顶边贴到它的**下缘之下**——只是往上挪开输入框焦点，**不翻到屏幕顶部**（那样会挡住上方对话）。下方空间不够时才顶到屏幕上沿。拿不到就静默退回贴底，不影响显示。
  - 定位分三级：`AXBoundsForRange`（精确光标）→ 复数 `AXSelectedTextRanges` → `AXPosition + AXSize`（整个输入框，粗判据）。多个候选时**精确优先**。
  - 探测路径：**焦点元素**（及其子层 / 父层）→ **焦点窗口的 AX 树里找可编辑区** → App 元素兜底。最后这条是必需的：Electron/Chromium 类App（含 WorkBuddy）里 `AXFocusedUIElement` 恒为 nil，输入框只出现在窗口的 AX 树里。
  - 找可编辑区有**两条判据，任一成立即命中**：① role 在白名单里（`AXTextField` / `AXTextArea` / `AXSecureTextField` / `AXSearchField` / `AXComboBox`）；② **能对选区给出「有面积的矩形」**——不只看 `AXSelectedTextRange` 存不存在，而是真去问 `AXBoundsForRange` 要矩形、且宽高不能同时为 0。第②条更本质：只要元素能给出**真实**的文本选区它就是可编辑区，哪怕 role 叫 `AXGroup`。Electron 的 role 会随版本变，光靠白名单早晚会对不上。
    - 「有面积」这三个字是踩过坑的：Chromium 里**大量** `AXGroup` 都返回 `{location=0, length=0}` 这种**空选区**，`AXBoundsForRange` 给出 `0x0`（还常在屏幕外）。只判「选区不是 nil」会把它当成输入框，而 Lua 里 `0` 是真值、光靠 `tonumber(location)` 挡不住 —— 于是一个垃圾候选就能把整个避让关掉，键盘照样压住输入框。
  - **还有一条不依赖 AX 的路：鼠标位置**（`M.useMouse`，默认开）。这是 **WorkBuddy 场景下唯一的出路** —— 它的真实 AX 树（2026-10-03 dump 工具修好后拿到）**只有 9 个节点，零文本元素**：`AXWindow`×1 / `AXGroup`×5 / `AXButton`×3，那 5 个 `AXGroup` 全是整窗大小 + 空选区。**不是我们没找对 role，是 Electron 根本没把输入框暴露给 AX。** A2 保留是因为它对原生 App（备忘录、Safari、终端）仍然有效。
  - **后台采样器从「模块加载时」就上线，不是等 `show()`**（`M.ensureMousePoll()`）。它要记的「点输入框 → 停顿」发生在键盘被打开**之前**；若在 `show()` 里才启动，账本里只有「鼠标此刻在菜单栏」这一笔（真机日志实测 `停了0.00s`），整条记账等于白做。
  - **`show()` 只读账本、绝不写入**。show 那一刻鼠标必然在菜单栏（触发入口就在那儿），让它参与记账等于把菜单栏塞进账本，正好毁掉要取的历史停顿点。
  - **假想输入区必须整个落在屏幕内，否则直接放弃避让**。账本里若只有菜单栏那个点（y≈14），造出来的矩形挂在屏幕顶之外，必然被「剔除屏外候选」干掉 —— 等于白跑一圈再回到贴底。日志里会明写「放弃鼠标避让」而不是含糊的「剔除屏幕外候选」。
    - **持续采样 + 记账「鼠标在哪儿停得最久」**（`M.mousePollInterval` 0.12s / `M.mouseAnchorHold` 0.25s）。**不能只看「打开那一刻鼠标在哪」** —— 触发入口是菜单栏图标，点它时鼠标必然在屏幕顶部（实测 y=14）。而真实动作序列是「点输入框 →（停顿）→ 移到菜单栏 → 点图标」，输入区对应的是**那个停顿的位置**，不是最后的位置。
    - 采样器用 **`hs.timer.doEvery`**（不是 `doInterval` —— 真机没这个 API，2026-10-03 踩过；周期定时器在 docs.json 的 **Constructor** 类别里，只查 Function 类别会误判成「没有周期定时器」）。建不起来时**降级成只在 show 时采样一次**并写日志，不让异常冒上去把整条避让关掉。
    - 它只是个**点**，没有高度，直接拿来跟面板比重叠毫无意义。所以在它**上方**造一个 `M.mouseAnchorHeight`（120）高的「假想输入区」，只取**下缘** —— 面板停在鼠标上方就不压住点击处。
  - 三类来源统一排序，**优先级**：AX 精确光标(1) > 鼠标位置(2) > 粗容器(3)。有真光标时不会被鼠标顶掉。排序带 `idx` 兜底做成**稳定排序**（`table.sort` 不保证稳定，同优先级时顺序未定义、会出现「有时用鼠标有时用 AX」的随机行为）。
  - 拿到候选后**剔掉中心点在主屏外的**，再从剩下的里挑。**不能因为「有一个候选在屏外」就整体放弃避让** —— 那等于让唯一一个坏候选否决所有人（鼠标位置那条路往往还在）。
  - 找到就**整层停止**，不再往命中元素底下挖：Chromium 常把输入框再套一层 wrapper，继续下降只会命中 wrapper 那个「整页大矩形」，反而更糟。
  - **大容器不动**：输入区可能大到无处可躲（Word / Pages / 浏览器的正文区能占满整个窗口高度）。这时认输、保持贴底，不凭模糊信息乱动；真解法是滚动正文让光标挪到上半屏。
  - 探测链路落盘 `/tmp/osk-ax.log`（>256KB 自动截断）：每次 show 记录各路径的候选矩形、最终位置与判断依据。「键盘为什么没躲开」在屏幕上完全看不出来，排查先看它。
  - **`M.logPath` 可注入日志路径** —— 测试必须改指到别处。共用同一个文件时真机记录会被测试输出埋掉（测试里的假坐标一眼就能认出来，但很容易误读成真机数据）。**诊断日志被污染 = 诊断日志失效。**
  - **找不到时会自动 dump 整棵 AX 树**到 `/tmp/osk-axtree.log`（各层节点数、role 统计、带矩形的节点、以及哪些节点能返回选区），不用手动敲命令。这是为了终结「猜 role / 猜深度」的盲猜：真实数据一摆出来，role 用什么、埋多深一目了然。
- **半透明**（`M.opacity`，默认 `0.88`，2026-10-05 从 0.78 调上来——Lin 说「稍微不透明
  一点点」，仍留一点透光但基本是实心的手感）：面板整体半透明，作为避让的兜底保险——避让总有兜不住的时候（输入区占满整页、或压根探测不到），挡不死，至少能透出下面的输入框。
  - 真正起作用的是 `canvas:alpha()` 这个**窗口级** alpha：不设它，元素颜色里的 alpha 只在面板**内部**混色，透不出下面被盖住的输入框。
  - **窗口级 alpha 与元素 alpha 是相乘的**，所以透明度只由 `M.opacity` 一个旋钮负责，元素颜色不跟着等比降（否则被乘两次、越调越糊）。键帽有 0.62 的下限、文字有 0.85 的硬下限——键盘的首要用途是看字认键。
  - 运行时可调，不用重载：`hs.osk.setOpacity(0.6)` 更通透 / `hs.osk.setOpacity(1)` 全实心（clamp 到 0.3~1）。
- 层级 `M.level = "assistiveTechHigh"`，并挂了 application watcher：任何 App 被激活就把面板重新 raise 一次（否则会被 Docker 等全屏窗口盖住）。
- **`hs.osk.dumpAXTree()`** —— 排障专用：把当前焦点窗口的 AX 整棵树 dump 到 `/tmp/osk-axtree.log`（每层节点数 + role 统计 + 带矩形的节点）。**当按 role 找输入框「命中 0 个」时，只有它能给出真相**（到底有哪些 role、埋在哪一层）；继续猜 role / 猜深度全是盲猜。
  - A2 命中 0 个时**自动跑一次**（每个 App 只跑一次），不用手动敲。
  - 遍历时**每个节点单独包 pcall**，**根层的 pcall 返回值也记进报告**：一个节点读 AX 抛异常不能毁掉整棵树的输出（2026-10-03 踩过——dump 只剩一行标题，看起来像「App 没暴露任何节点」，其实是什么都没写出来）。文件末尾会写「共 N 个节点 / walk 失败 M 个」，N=0 时额外写明原因。
  - **2026-10-03 修掉两个让它「从没真正工作过」的 bug**（在此之前它显示的「可编辑文本区：一个都没有」全部是假的）：
    - `counts` 初始化成 `{}` ⇒ `counts.total` 是 nil ⇒ walk 第一行 `counts.total > 400` **直接抛** `attempt to compare nil with number` ⇒ 一个节点都没走成，报告却写成「0 个节点 / walk 失败 0 个」——**把自己的失败写成了「外部世界没有数据」**。
    - `rectOf` / `validRect` 定义在 `dumpAXTree` **后面**，Lua 里后面的 local 前面不可见 ⇒ dump 走到判据 2 必抛 `attempt to call a nil value (global 'rectOf')`。已把定义前移。
    - 教训：**诊断工具必须有测试**。dumpAXTree 此前零覆盖，所以这两个 bug 一个都没被发现，还让我据此得出「Electron 不暴露 AX」的错误结论。

### window.lua — 窗口管理热键

9 个 `⌘⌥⌃` 组合键，全部作用于当前焦点窗口；焦点不在任何窗口上（Finder 桌面等）时静默退出。

| 键 | 动作 |
| --- | --- |
| `F` | 铺满当前屏幕（`usableFrame`） |
| `←` `→` | 窗口**平铺**到左/右半屏（宽减半、**高度保持满**） |
| `↑` `↓` | 窗口**平铺**到上/下半屏（高减半、**宽度保持满**） |
| `M` | 左右各留 12%（窗口居中，左右等宽） |
| `N` | 四边各留 20%（窗口居中） |
| `[` `]` | 窗口移到上/ 下一块屏幕，到头后环绕 |

**方向键必须同时改位置和尺寸**（2026-10-03 修）。原先的 `placeAt()` 只挪位置不动尺寸，
而它挪动的幅度是 `max.w - frame.w` —— **窗口一旦满屏，这个差就是 0**，
`left` 和 `right` 算出来完全是同一个值，四个方向等于没绑。真机日志实锤：
窗口 `(0,30 1600x884)` 已经是满屏宽，`left`/`right` 全部原地不动
（上下最多挪 29px，肉眼看不出来）。

> 顺带一提，同一份日志里 `[f] 作用到窗口 (320,207 960x600)` 是**生效**的 ——
> `F` 会改尺寸。这就是当时的 A/B 对照证据：改尺寸的键有效，只挪位置的键无效。

`snapHalf(gx, gy)` 里 **`0.5` 的含义是「这一轴保持满长」，不是「居中」**：
`left`/`right` 传 `gy=0.5`（满高），`up`/`down` 传 `gx=0.5`（满宽）。传错成 `0`
会变成四分之一块 —— 这个坑踩过一次，测试当场报出 `(0,0) 720x450`（高度也被砍半了）。

**焦点被 Hammerspoon 自己占住时的兜底（2026-10-03 修）**

`withWindow()` 会排除 Hammerspoon 自己的窗口，并在焦点落在那儿时**回退到最近一次的真实目标窗口**。

起因：osk 的 `show()` 里 `M._canvas:show()` 会**激活 Hammerspoon**（NSWindow 的
`makeKeyAndOrderFront`，激活是异步的），之后靠 `restoreFocusOnce` 在 0/0.1/0.3/0.6s
四个点把前台 App 抢回来。只要有一次没成功，`hs.window.focusedWindow()` 返回的就是
**键盘画布**，方向键的 `setFrame` 全作用在键盘面板上 —— 现象是「四个方向一起没反应」，
很容易误判成热键没绑定。现在这种情况会打日志并改用历史窗口。

诊断日志：`/tmp/hs-window.log`，每次按热键记两行（改之前的窗口/屏幕 + `改后→` 的结果）。
**第二行是关键** —— 只记改之前的看不出效果，排查「方向键不生效」时差点误判成
`setFrame` 没被调用；真正的问题是「调了，但算出来的值等于原值」。日志还会显式标出
`← 与改前完全相同（等于没动）`。

判断方法：

- 完全没有 `[left]` 这行 → 热键真没触发，去查 kbswap 的 `⌘/⌥` 交换状态
- 有 `[left]`，但标着`等于没动` → 算出来的值和原来一样（上一轮修的就是这个）
- 有 `[left]` 且 `改后→` 显示新 frame → 生效了，问题在别处

## 开发约定

- 改完配置在 Hammerspoon 菜单栏手动 **Reload Config**，不自动重启。
- 模块改动配套离线测试（lupa 驱动的 Lua 断言，在 `.workbuddy/skills/hammerspoon-config-test/`），改前跑一遍防回归：

  ```sh
  cd ~/.hammerspoon/.workbuddy/skills/hammerspoon-config-test
  ~/.workbuddy/binaries/python/envs/default/bin/python run-lua-test.py example-<module>-test.lua
  ```

  注意带 `os.exit()` 的测试（clipboard / spoon）要单独跑——`SystemExit` 会终止运行器。
- 涉及权限的功能先想 TCC / 代码签名；不要动 `/Applications/Hammerspoon.app` 的 Info.plist（会破坏签名与已有授权）。
- **写 Hammerspoon 脚本时热键键名一律小写**（`f` / `left` / `right`，不是 `F` / `Left`）。`hs.keycodes.map` 里没有大写项，传大写不可靠。
- 模块不要往 `_G` 里撒全局变量，一律 `local` + `return M`。
- **屏幕坐标全是「左上原点、y 向下」**：`hs.screen:frame()`、`hs.canvas`、
  `hs.window:frame()`、`hs.mouse.getAbsolutePosition()`、`hs.eventtap.event:location()`、
  AX 的 `AXPosition`/`AXBoundsForRange` 都是这一套，彼此直接比较即可。
  **任何一处做 y 翻转都是 bug**（依据：`libcanvas.m` 的 `RectWithFlippedYCoordinate`
  在 Lua 侧 ↔ NS 侧之间做翻转，说明 Lua 侧就是 y 向下那套）。
